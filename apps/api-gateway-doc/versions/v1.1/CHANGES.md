## Requirement levels (modality rule)

- **shall / shall not** ← README *must*, *required*, *mandatory*, *not permitted*, and items marked 'Required' or 'separate' in the README capability summary (§38).
- **should / should not** ← README *should* where it expresses a preference or recommendation.
- **may** ← README *can*, *may*, *optional*.
- Descriptive statements in the README (for example 'The application remains responsible for…', 'The Gateway validates…') are written as 'shall'.

## Inconsistencies in the README and how they were resolved

1. **Required vs. optional.** README §13/§15/§16 called rate limiting, caching and schema validation optional, while §38 called them 'Required capability'. Resolved as: the Platform shall provide the capability; whether it is enabled for a given API is the Application Team's decision (Section 1.4, Appendix A). Confirmed during review: all three stay fully optional per API and are recommended where they can help.
2. **Credentials vs. tokens.** README §40 item 8 said long-lived 'access tokens' should not be transmitted; §6 makes the distinction between long-lived client credentials and short-lived access tokens. Corrected to 'credentials' (Section 4.3).
3. **Structure.** README §5.1 (C2B) was an orphan and B2B was a separate top-level section (§6); both now sit under Chapter 4. §33–§36 were titled 'Security Boundary' although §34 (load balancer) and §36 (application) are not security topics; retitled 'Platform Boundaries' (Chapter 12).
4. **Duplicates merged.** Load-balancer boundary (§9, §34), the Gateway/application authorization split (§7, §36), Git as source of truth and GitOps (§20, §21), the two near-identical distributed-runtime diagrams (§28, §29), and the 26 closing principles (§40) versus §3, are each stated once.
5. **Terminology.** 'Control plane', 'management layer', 'management plane' and 'central management' are unified as 'Management Plane'; 'the platform', 'the API platform' and 'the Gateway platform' are unified as 'the Platform' / 'the Gateway' as defined in Section 1.5.

|---|---|
| Token lifetime | Defined by the owner of the Identity Provider; the document says so (Section 4.1, note). |
| Transport security | Traffic inside the cluster, including Gateway to backend, uses HTTP; no minimum TLS version is defined (Section 11.2, note). 'HTTPS at required boundaries' is kept as a guardrail example, without saying which boundaries. |
| Maximum request size | No maximum is defined (Section 11.2, note). 'Maximum request size' stays in the README's list of guardrail examples. |
| Availability measurement | 99.9% applies during regular operation; planned maintenance is excluded (Section 10.1). |
| Management Plane | The Data Plane runs on its last known configuration indefinitely, and the Management Plane should be restorable within one hour (Section 10.4). |
| Retention | No log or audit retention period is defined (note in Section 9.3). |
| Sensitive payloads | Payloads involving sensitive information should not be logged; what is sensitive is defined per API by the Application Team (Section 9.1). |
| Health checks beyond HTTP | Read as: regular health checks apply to all API technologies, with no protocol-specific mechanism (Section 5.4, note). Please confirm this reading. |
| Anonymous APIs | Not permitted (new requirement in Section 4.1). |
| Governance body | Not yet defined; recorded in Section 11.5 and kept open as OI-01. |
| Exception approval | Exceptions are approved by the Security Managers, a defined team (Section 11.6). The team's name is a placeholder to fill in (Section 1.5). |
| Capability enablement | Rate limiting, caching and schema validation stay fully optional per API and are recommended where they can help (Section 5.7, 6.2, 6.3). |
| Consumer configuration in Git | Git holds consumer identity, entitlements (APIs and operations) and rate limits; credentials are never in Git (Section 8.1). Not answered: whether consumers can also be created at runtime, for example through the Developer Portal. |
| Security core made mandatory | C2B use of the IdP with short-lived tokens, the B2B token exchange, no long-lived credential on every request, and no reliance on undocumented manual production configuration are now 'shall' (see the change table above). Other 'should' requirements are unchanged. |
| Scope gaps | Read 'yes' as: WebSocket/streaming, east-west traffic, multi-tenancy and non-production environments are in scope (Section 1.2). Please confirm this reading. |
